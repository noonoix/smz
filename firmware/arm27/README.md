# ARM 2.7 — Human mouse and custom USB identity

`ams_board27.ino` is the Pro Micro/ATmega32U4 application firmware. The SparkFun Pro Micro FQBN is only a hardware/toolchain target; it is not an allowed final USB product identity.

## USB identity contract

Classroom Studio is the source of truth for board identity:

1. The Board Preparation flow chooses or creates the custom VID, bootloader PID, application PID, manufacturer, product and serial.
2. The customized Caterina bootloader is written only through the recovery/ISP path.
3. Classroom Studio installs the matching custom board definition. Its `build.vid`, `build.pid`, `build.usb_product` and `build.usb_manufacturer` values are compiled into the application firmware.
4. Normal updates use the application-only HEX and Caterina/AVR109 without erasing or replacing the bootloader.
5. After upload, the application must enumerate with the provisioned application VID/PID and custom strings. `Arduino Leonardo`, `SparkFun Pro Micro`, `Pro Micro` and `Leonardo` are forbidden as the final application identity.

Do not build a production image by selecting a stock Leonardo or Pro Micro board entry. That would preserve the correct CPU target but replace the provisioned application identity with a generic Arduino/SparkFun identity. Use the board definition generated by Classroom Studio, or pass the same identity values explicitly to the build.

The bootloader and application use sibling PIDs. A temporary bootloader identity during 1200-bps reset is expected; the final runtime identity must be the custom application identity.

CI compiles the firmware with an explicit non-Arduino Classroom identity and checks the resulting application HEX for the custom strings and for forbidden generic names. Production builds must substitute the identity selected in Classroom Studio.

## Human mouse protocol

Capability negotiation:

- `HVER` → `OK|HVER|2.7.0|HMOUSE=1`

Configuration and movement:

- `HCFG|speedMin,speedMax,moveMin,moveMax,curveMin,curveMax,beforeMin,beforeMax,afterMin,afterMax`
- `HPAUSE|midChance,midMin,midMax,idleEveryMin,idleEveryMax,idlePauseMin,idlePauseMax,overChance`
- `HMOVE|x,y`
- `HRANDOM|x,y,w,h`

`HCFG` deliberately leaves the profile unarmed. Only a valid following `HPAUSE` makes movement executable. Negative, reversed and out-of-screen ranges fail closed. Movement is curved, acceleration/deceleration shaped, overshoot/correction capable, pause-aware and `HALT`-abortable. Mid-movement pauses occur inside motion legs. Legacy ARM 2.6 commands and encrypted USB behavior remain available.

The Pico lightweight runner already dispatches `RMOUSE` and `MOVETO` through ARM 2.7 capability negotiation. A bundle that needs these commands must fail closed against ARM 2.6.
