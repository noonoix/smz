## چرا v0.9.20 بدتر به نظر رسید

رکورد اجرای واقعی (ضبط‌شده با رکوردر AMS قدیمی — خط اول `Key Up : F1` هاتکی اجراست)
دو چیز را اثبات کرد:

### ۱. برد به KTEXT تک‌کاراکتری هم تاخیر سمت‌برد اعمال می‌کند

کد v0.9.20 هر کاراکتر را با هدر اصلی `KTEXT|hmin,hmax,<c>` می‌فرستاد و **علاوه بر آن**
مکث `NextRandom(hmin,hmax)` هم سمت اپ اضافه کرده بود. رکورد:

```
میانه‌ی cadence کلیدها: 408ms   ≈   برد ~190ms   +   اپ ~190ms
(کانفیگ: hmin=80, hmax=300 → انتظار ~190ms، دریافت ۲ برابر)
```

یعنی تایپ با **نیم‌سرعت** اجرا می‌شد — همان «بدتر شده».

### ۲. هر op هنوز کانال تک‌سریال را اشغال می‌کرد

چون برد تاخیر را خودش اجرا می‌کند و bridge تا پاسخ نهایی صبر می‌کند (`_ioLock`)،
هر op صدها میلی‌ثانیه کانال را نگه می‌داشت → میکرو-فریزهای موس.
رکورد: فریزهای **۸٫۶s** و **۶٫۷s** موس حین تایپ پیوسته (۳۴ و ۲۸ کلید در خلال).

## رفع — v0.9.21

اصل معماری: **تمام پیسی‌گذاری انسانی سمت اپ؛ همه‌ی opهای برد فوری.**

```csharp
// حالت موازی — برای هر کاراکتر:
await Send("KTEXT|0,0," + c);                        // op فوری ~10ms
await PausableDelay(NextRandom(hMin, hMax), ct);     // cadence انسانی سمت اپ
```

- `ChunkKtextForParallel` حالا هدر را به `KTEXT|0,0` بازنویسی می‌کند.
- هر op برد ~۱۰ms کانال را نگه می‌دارد → بین کلیدها کانال برای waypointهای موس آزاد است.
- cadence تایپ دقیقاً همان کانفیگ کاربر است (hmin..hmax) — نه دو برابر.
- این همان مدل اپ AMS قدیمی است: فرمت رکوردش `Key Down/Key Up + Delay` بود — یعنی
  opهای فوری + پیسی‌گذاری سمت اپ.

**پلن جایگزین مستندشده:** اگر فریم‌ور دلیل delay=0 را floor کند، جایگزین
`KDOWN|vk` / `KUP|vk` به‌ازای هر کاراکتر است — هر دو در README «verified against
firmware 1.6» هستند و در strings فلش برد دیده می‌شوند.

### چیزهایی که دست نخوردند (عمدی)

- مسیر غیرموازی typeText: همان chunkهای ۶۰ کاراکتری board-paced (اثبات‌شده، خوب).
- مکث‌های موس (before/after/idle breaks): کانفیگ خود کاربر است — الگوی انسانی.
- لنگر موس (`_mouseAnchor`): رکورد صفر تله‌پورت نشان داد — کار می‌کند، حفظ شد.
