## گزارش کاربر

در یک پلن با `Find Image On Screen` (BMP Similar = **70%**، scope = **entireScreen**، timeout = **3s**)،
تصویر الگو یک آیکون بود ولی موتور یک آیکون **کاملاً متفاوت** در تسک‌بار را HIT اعلام کرد.
دو تصویر از نظر انسانی هیچ شباهتی نداشتند.

---

## ریشه‌یابی — ۷ علت

### ۱. رنگ کاملاً دور ریخته می‌شد (علت اصلی)

```csharp
// قدیم — ToGrayPooled
gray[i] = (byte)((raw[i] + raw[i + 1] + raw[i + 2]) / 3);
```

میانگین ساده‌ی B/G/R یعنی:

| رنگ | B | G | R | خاکستری قدیم `(B+G+R)/3` | luma جدید |
|---|---|---|---|---|---|
| قرمز خالص | 0 | 0 | 255 | **85** | **76** |
| سبز خالص | 0 | 255 | 0 | **85** | **149** |
| آبی خالص | 255 | 0 | 0 | **85** | **29** |

هر سه رنگ به عدد **۸۵** نگاشت می‌شدند. یعنی دو آیکون هم‌شکل ولی با رنگ متفاوت
پس از تبدیل، بایت‌به‌بایت **یکسان** می‌شدند و امتیاز NCC دقیقاً **1.000** می‌گرفتند.

### ۲. NCC ذاتاً نسبت به روشنایی و کنتراست کور است

`Ncc` هم میانگین الگو و هم میانگین پنجره را کم می‌کند و بر `nDen * hDen` تقسیم می‌کند.
نتیجه: فقط **الگوی تغییرات** سنجیده می‌شود، نه مقادیر مطلق.
یک آیکون قرمز و یک آیکون آبی با شکل یکسان، از نظر luminance یک **مقیاس‌دهی خطی** از هم
هستند — و NCC نسبت به مقیاس‌دهی خطی ناوردا است، پس امتیاز دقیقاً **1.000** می‌شود.

> این نکته مهم است: gate رنگ اینجا یک «کمربند ایمنی اضافه» نیست، **تنها چیزی است که
> این حالت را رد می‌کند**.

### ۳. معنای آستانه غلط بود

```csharp
// قدیم
double thr = px < 32 ? 0.85 : Math.Clamp(similarity, 1, 100) / 100.0;
```

«۷۰٪ شباهت» در UI مستقیماً به `NCC ≥ 0.70` ترجمه می‌شد. برای template matching روی
گرافیک UI این عدد **بسیار شل** است؛ تطبیق واقعی معمولاً بالای ۰٫۹۵ می‌افتد و ۰٫۷۰ عملاً
«هر چیزی که مبهم شبیه باشد» را قبول می‌کند.

### ۴. گارد الگوی کوچک هرگز فعال نمی‌شد

`px = Width * Height` بود، پس `px < 32` یعنی مساحت کمتر از حدود ۶×۶ پیکسل.
یک آیکون ۱۶×۱۶ برابر ۲۵۶ پیکسل است و همیشه آستانه‌ی شل خام را می‌گرفت.
کامنت کد نوشته بود «32 px²» که با خود کد در تناقض بود.

### ۵. هیچ آزمون ابهام / نفر دوم وجود نداشت

```csharp
if (score > bestScore) { ... }   // هر چیز بالای آستانه پذیرفته می‌شد
```

اگر ۵۰ نقطه روی صفحه بالای آستانه بودند، موتور صرفاً اولی/بهترینِ لحظه‌ای را برمی‌گرداند
بدون اینکه بپرسد «آیا این واقعاً یکتا است؟».

### ۶. پویش گام‌دار (step = 3) می‌توانست روی محل غلط قفل شود

پویش درشت با گام ۳ فقط x ∈ {0, 3, 6, …} را نمونه‌برداری می‌کرد.
روی گرافیک UI با لبه‌های تیز، یک پنجره با فقط **۱ پیکسل** انحراف می‌تواند NCC را به زیر
**۰٫۶۲** بیندازد. پس اگر محل واقعی روی مضرب ۳ نبود، **هرگز نمونه‌برداری نمی‌شد** و
موتور روی یک محل غلطِ بالای آستانه می‌نشست.

### ۷. کانال آلفا / شفافیت نادیده گرفته می‌شد

الگوها با `Format24bppRgb` قفل می‌شدند؛ پیکسل‌های شفاف مثل پیکسل‌های مات وزن می‌گرفتند.

## معماری جدید — سه دروازه

مسیر تطبیق حالا `MatchCore` است و یک کاندید فقط وقتی HIT اعلام می‌شود که **هر سه** را رد کند:

```
            ┌─────────────────────────────────────────────┐
  capture → │ Gate 1 — SHAPE   : NCC ≥ MapSimilarity(s)   │
  (BGR)     │                    (کف 0.95 برای الگوی کوچک)│
            ├─────────────────────────────────────────────┤
            │ Gate 2 — DISTINCT: margin ≥ 0.02            │
            │                    یا second ≥ 0.97         │
            ├─────────────────────────────────────────────┤
            │ Gate 3 — COLOUR  : ColorMad ≤ ColorTol(s)   │
            └─────────────────────────────────────────────┘
```

### Gate 1 — شکل (کالibre‌شده)

```csharp
public static double MapSimilarity(int similarity)  // 0.85 + 0.145 * s * s
public static double ColorTolerance(int similarity) // 8.0 + (100 - s) * 0.35
private const int SmallTemplateArea = 32 * 32;      // کف minScore روی 0.95
```

درصد UI دیگر مستقیماً NCC نیست. کف مطلق **۰٫۸۵** است حتی روی ۱٪،
و الگوهای کوچک‌تر از ۳۲×۳۲ کف **۰٫۹۵** می‌گیرند (باگ #۴ حل شد).

| UI % | آستانه NCC قدیم | آستانه NCC جدید | تلورانس رنگ |
|---|---|---|---|
| 1 | 0.010 | 0.850 | 42.6 |
| 30 | 0.300 | 0.863 | 32.5 |
| 50 | 0.500 | 0.886 | 25.5 |
| **70** | **0.700** | **0.921** | **18.5** |
| 85 | 0.850 | 0.955 | 13.2 |
| 100 | 1.000 | 0.995 | 8.0 |

### Gate 2 — یکتایی

```csharp
double margin = cand.Value.score - cand.Value.second;
bool distinctive = margin >= 0.02 || cand.Value.second >= 0.97;
```

`second` بهترین رقیبِ **غیرهم‌پوشان** است (فاصله‌ی حداقل `max(nw, nh)`).
بند دوم عمداً وجود دارد: اگر یک آیکون واقعاً **دو بار** روی صفحه باشد، هر دو نمره‌ی ~1.000
می‌گیرند و نباید به‌عنوان «ابهام» رد شوند — این یک تکرار مشروع است، نه ابهام.

### Gate 3 — رنگ

```csharp
private static double ColorMad(byte[] hayRgb, int hw, int x0, int y0,
                              byte[] needleRgb, int nw, int nh)
```

میانگین قدرمطلق اختلاف روی **هر سه کانال B/G/R** در محل نهایی.
این دقیقاً همان چیزی است که باگ گزارش‌شده را می‌گیرد:

```
آیکون آبی در برابر الگوی قرمز → colour MAD = 64.5  >  tol 18.5  ⇒ REJECT
```

و حتی روی similarity = 1 (تلورانس ۴۲٫۶) هم رد می‌شود.

### خاکستری‌سازی درست

```csharp
// جدید — GrayFromRgbPooled، وزن‌های ITU-R
gray[p] = (byte)((rgb[i] * 114 + rgb[i + 1] * 587 + rgb[i + 2] * 299) / 1000);
```

`ToGrayPooled` حذف شد. حالا `ToRgbPooled` یک بافر BGR فشرده (stride = `width * 3`)
برمی‌گرداند و padding مربوط به GDI را با `Array.Copy` سطر‌به‌سطر حذف می‌کند،
تا Gate 3 به داده‌ی رنگی واقعی دسترسی داشته باشد.

## جست‌وجوی هرمی (باگ #۶)

پویش گام‌دار حذف شد. مشکل بنیادی این بود که **نمونه‌برداری گام‌دار aliasing ایجاد می‌کند**؛
هیچ گام امنی وجود ندارد چون روی لبه‌های تیز حتی ۱ پیکسل انحراف امتیاز را نابود می‌کند.

جایگزین: **میانگین‌گیری جعبه‌ای (box-average)** که به‌جای aliasing، **نسبت به جابه‌جایی
مقاوم** است.

```csharp
private static int PyramidFactor(int nw, int nh)
    => Math.Max(1, Math.Min(4, Math.Min(nw, nh) / 12));

private static byte[] DownscalePooled(byte[] srcBuf, int w, int h, int f,
                                     out int dw, out int dh);
```

مراحل:

1. `f = PyramidFactor(nw, nh)` — الگوی باریک‌تر از ۱۲px در هر محور با `f = 1` جست‌وجو می‌شود.
2. هر دو تصویر (صفحه و الگو) با میانگین جعبه‌ای کوچک می‌شوند.
3. جست‌وجوی **جامع با گام ۱** در مقیاس درشت — «هیچ حفره‌ای در شبکه نیست که قله در آن پنهان شود».
4. آستانه‌ی درشت **شل** است: `coarseMin = Math.Max(0.40, minScore - 0.25)`.
5. حداکثر ۸ کاندید **جدا از هم** نگهداری می‌شود (`InsertCandidate`).
6. هر کاندید در **رزولوشن کامل** پالایش می‌شود (`RefineAt`، شعاع `f + 1`).
7. آستانه‌ی واقعی **فقط بعد از پالایش** اعمال می‌شود.

حالت خاص: اگر کوچک‌سازی منجر به ابعاد نامعتبر شود، بافرهای pool برگردانده می‌شوند و
کد به `f = 1` برمی‌گردد.

### هزینه — صفحه ۱۹۲۰×۱۰۸۰، الگوی ۴۰×۴۰، f = 3

```
جامع در رزولوشن کامل :   3,132,993,600 ضرب
گام‌دار قدیم (step 3) :     348,110,400 ضرب
هرمی جدید (f = 3)     :      36,933,936 ضرب   ← 9.43× ارزان‌تر از step-3
```

یعنی روش جدید هم **دقیق‌تر** است و هم **سریع‌تر**.

## ⚠️ تغییر رفتار — مهم برای کاربر

کالibre‌شدن آستانه یک **تغییر رفتاری** است، نه صرفاً رفع باگ:

- پلن‌های ذخیره‌شده حالا **سخت‌گیرانه‌تر** ارزیابی می‌شوند.
- بعضی تطبیق‌هایی که قبلاً «کار می‌کردند» در واقع false positive بوده‌اند و حالا رد می‌شوند.
- اگر یک مرحله‌ی `Find Image` بعد از ارتقا دیگر پیدا نمی‌کند:
  1. BMP الگو را **دوباره بگیرید** (مخصوصاً اگر با DPI یا تم متفاوتی گرفته شده).
  2. مقدار similarity را کمی پایین بیاورید — ولی توجه کنید کف مطلق ۰٫۸۵ است.
  3. مطمئن شوید الگو ناحیه‌ای با **کنتراست کافی** دارد؛ الگوی تخت هرگز تطبیق نمی‌خورد.
